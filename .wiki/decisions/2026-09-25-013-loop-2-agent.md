# feat: loop stage 2 — turns outlive windows, approvals are recorded, and identical writes are allowed during a session

What. `session_state.plans` reads series folders from newest first, and within a single folder, reads earlier numbers first. SessionStart shows `0-overview` and the next remaining stages instead of stages 7 and 6 for task turn reconnection. Turns run on threads, and events are stacked in a `Run` buffer placed in each task tree with `seq` and `turn` attached - `POST /api/work/say` bites the tail of the buffer. …

Why. The specification task and review loop of stages 3 and 4 are long. If an automatic loop is placed on a turn that dies when the window is refreshed, the loop is tied to the window's lifespan. Since the turn sent by the loop is also approved for every write, there must first be a way to avoid asking for the same write every time and a record of what has been approved. Two points differ from the plan. The permission to close a window is not `core:window:allow-close` but `core:window:allow-destroy`. If there is a close listener, Tauri does not close the window and the screen calls `destroy()` (`@tauri-apps/api` 2.11). The Codex token is not the difference of `total` but the sum of `last`. …
