# feat: loop stage 3 — The conversation ends with a single specification, [Start] assigns tasks based on that specification, and the server runs the gate again before opening a PR

What. `tool/main/specs.py` (new file) is the sole owner of `raw/specs/<repo>/<id>.json`. Reading, checking, saving, and changing states are done only here - reject empty `goal`. The gate (the `gate_cmd` of the adapter) is always the first item of `done` and only once. If there is no `gate_cmd` in the adapter, instead of a card, "Connect first" - organize `slug` in lowercase, and if it overlaps with the specification, task tree folder, or branch, `-2`, `-3`. …

Why. "→ Task" passed only one question and one answer, the to-do list was an empty line, and there was no system prompt in the task session. What is decided in the conversation must remain as a single specification to link the task tree, PR, review round, and decision record. Since the agent's "Done" is not evidence, the server opens a PR only after running the same gate again. Decisions that filled the gaps left by the plan are recorded in "Decisions made during implementation" in `docs/plans/loop/3-spec.md` (verification of plan row sources, criteria for the same conversation, including branches in overlaps, push/PR failures are `fault`, order of plan row turns, etc.).
