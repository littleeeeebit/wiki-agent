AI 코딩 에이전트는 세션이 끝나면 배운 것을 잊습니다. wiki-agent는 교훈을 적어 두고, 필요한 순간에 에이전트 눈앞에 먼저 펼쳐 줍니다. 그 위에서 위키에 묻고, 일을 맡기고, 리뷰 루프로 돌려받는 데스크톱 앱이 돕니다.

문제

적어 둔 교훈이 행동을 못 바꾼다

프로젝트 A · 월요일리뷰를 엉뚱한 셀에 보냄세션 종료 — 기억 사라짐
프로젝트 B · 수요일리뷰를 엉뚱한 셀에 보냄세션 종료 — 기억 사라짐
프로젝트 A · 금요일리뷰를 엉뚱한 셀에 보냄…

문서로 남겨도 소용없었습니다. 문서는 안 읽히면 그만이니까요. 부족한 건 저장 공간도 검색도 아니었습니다. 그래서 이 위키가 하는 일은 딱 둘입니다. 반복되는 지시는 스킬로 굳히고, 검사로 바꿀 수 있는 규칙은 검사로 바꿉니다. 판단이 필요한 나머지는 글로 둡니다. 판단할 일을 기계로 막으면 헛경보가 작업을 멈추기 때문입니다.

어디에 적나

서랍은 세 개, 여기엔 둘만

operator/사람을 따라가는 규칙리뷰 루프 방식 · 결정은 선택지로 묻기 · 파일은 diff로 고치기
craft/기술을 따라가는 규칙먼저 재현하기 · 초록불도 의심하기 · 위험한 git 명령 막기
project그 저장소만의 규칙각 프로젝트의 .wiki/에 둡니다. 남의 지뢰가 섞여 들어오는 것 자체가 사고라서.

손으로 쓴 규칙 페이지는 몇 장뿐입니다. 나머지 문서는 세션 시작 때 목록만 한 번 넣어 주고, 본문은 에이전트가 필요할 때 엽니다. 규칙이 실패하는 방식은 “안 읽었다”라서 훅이 밀어 넣고, 문서가 실패하는 방식은 “있는 줄 몰랐다”라서 목록이면 충분합니다.

세션 하나에서 일어나는 일

훅이 끼어드는 세 순간

SessionStart세션을 열 때
  • 현재 브랜치와 작업트리 상태
  • 하다 만 계획의 남은 단계
  • 최근 결정과 그 이유
  • 모든 문서의 목록
UserPromptSubmit말을 걸 때마다
  • 말에 걸린 규칙 페이지
  • 한국어 말의 영어 번역
  • 매번 붙는 짧은 계약 몇 개
PreToolUse도구를 쓰기 직전
  • 계산해야 보이는 위반만 검사
  • 예: 진행 설명의 언어, 파일을 통째로 되쓰기, 테스트 출력을 파이프로 가리기
Stop턴이 끝날 때
  • 위키를 저장소의 실제 상태에 맞춤
  • “이어서 하겠다”고 적고 도구 없이 끝낸 턴을 되돌려 다시 시킴

“뭘 하던 중이었지”는 어떤 말에도 걸리지 않으니, 세션 시작 때 따로 한 번 넣습니다. 같은 세션에서 이미 통째로 받은 규칙은 다음부터 핵심 문단만 보내 토큰을 아낍니다. 그리고 훅은 고장 나도 막지 않습니다. 번역 키가 없거나 스크립트가 터져도 작업은 그대로 갑니다. 일을 멈추는 강제는 결국 사람이 꺼 버리기 때문입니다.

어떻게 지키게 하나

싼 칸부터 오르고, 막히는 칸에서 멈춘다

  1. 1명령 자체를 금지permissions.deny — 위반이 명령 모양일 때한 줄
  2. 2말에 맞는 규칙을 주입심장UserPromptSubmit 훅 — 각 페이지가 자기 triggers를 적어 둔다정규식 몇 줄
  3. 3반복 지시를 절차서로skills/ — 순서가 틀릴 수 없게파일 하나
  4. 4도구 실행 직전 검사PreToolUse 훅 — 계산해야 보이는 위반오탐 위험
  5. 5그냥 글판단이 필요한 것안 지켜질 수도
두 언어

왜 에이전트는 영어로 쓰고, 사람은 한국어로 읽나

한때 위키 페이지, 훅 프롬프트, 진행 보고가 전부 한국어였습니다. 그러자 에이전트가 한국어로 생각하고 쓰는 동안 눈에 띄게 덜 정확해졌습니다. 그래서 에이전트가 닿는 모든 표면은 영어(문서 · 프롬프트 · 진행 보고 · 코드 주석)로 쓰고, 그 위에 Gemini 번역을 한 겹 덮어 사람은 한국어로 쓰고 한국어로 읽습니다. 두 언어는 타협이 아니라 두 독자입니다.

데스크톱 앱

한 창에서 묻고, 맡기고, 돌려받는다

왼쪽엔 프로젝트와 작업 목록, 가운데엔 대화, 오른쪽엔 선택한 작업의 에이전트 · 리뷰 · 터미널이 있습니다. 가운데 대화는 목적에 따라 포커스 넷으로 나뉩니다.

다음 작업후보를 내고, 되물어, 명세로 정한다계획의 남은 단계 · 열린 PR · 최근 결정 · 경고를 모아 후보를 내고, 선택지로 되물어 명세 카드로 끝냅니다
리팩터링목적 하나를 골라 조사하고 명세를 만든다동작 보존 정리 · 불필요한 복잡도 정리 · 구조·성능 근본 수정 중 하나로 저장소를 읽기 전용 조사합니다
위키문서와 기록으로 답한다저장소의 문서 · 계획 · 결정 · 코드를 근거로 답하고, 근거를 열어 볼 수 있습니다. “왜 안 되나”는 로그부터
회고오늘 어긋난 자리를 센다오늘의 커밋과 대화에서 정정 · 반복 지시 · 멈춤을 세어 규칙 후보를 냅니다
명세 카드 하나가 머지까지
  1. [시작]선택한 체크아웃에 작업 브랜치를 만들고, 명세를 시스템 프롬프트로 받은 에이전트가 일합니다
  2. 게이트에이전트의 “통과했다”가 아니라 서버가 다시 돌린 검사 결과를 믿습니다. 통과해야 PR
  3. [리뷰 루프]읽기 전용 리뷰 셀이 라운드마다 읽고, 지적은 작업 셀로. 머지 가능까지
  4. [머지]리뷰가 허용한 바로 그 커밋에 묶어 스쿼시 머지하고, 브랜치를 정리합니다
  5. 결정 기록명세의 결정과 이유가 .wiki/decisions/로. 다음 세션 시작 때 다시 실립니다

작업 세션은 끝내기 전에 TDD가 남긴 중간 테스트를 정리하고 보고합니다. 빠뜨리면 서버가 한 번 더 요청하고, 그래도 없으면 작업을 멈춥니다. 대화의 문맥 비우기는 원문과 요약을 그 저장소의 .wiki/memory/에 남겨, 다음 질문의 근거가 되게 합니다.

가운데 탭에서는 규칙이 이어진 지도, 저장소의 앱 구조 그림(.omm), 살아 있는 셀과 최근 100번의 실행을 모은 스위트를 봅니다. 휴대폰을 연결하면 밖에서도 작업을 보고 지시나 승인을 보낼 수 있고, 새 버전이 나오면 왼쪽 아래 카드가 받아서 다시 빌드합니다.

리뷰와 머지

“통과했다”는 말보다 증거를 믿는다

리뷰 루프는 작업 셀과 분리된 읽기 전용 리뷰 셀이 돌립니다. 여러 PR을 동시에 돌릴 수 있고, 동시 실행 수는 설정에서 제한합니다. 루프 안에는 다음 장치가 있습니다.

작업에 맞는 리뷰 기준계획 문서 · 코드 · 둘 다인 PR은 서로 다른 기준으로 읽습니다. 리팩터링은 동결한 동작 보존 검사를 라운드마다 다시 돌리고, 의무나 영수증이 바뀌면 승인을 무효로 합니다
반복되는 지적엔 조사부터고쳤다던 심각한 지적이 다시 나오거나(A-A, A-B-A) 7라운드부터도 거절되면, 다음 수정 전에 웹 조사를 먼저 합니다. 같은 문제에 조사와 수정을 두 번 하고도 안 되면 멈춥니다
선행 리뷰구현을 계속하기 전에 독립 판단이 필요한 작업은 읽기 전용 셀의 판정을 먼저 받습니다. 판정은 구현을 풀어 줄 뿐, 최종 승인을 대신하지 않습니다
최종 게이트는 한 번, 한 주인수정 라운드는 관련 검사만 돌리고, 리뷰가 허용한 커밋에서 전체 게이트를 한 번 돌립니다. 공개 저장소에 CI가 있으면 CI가, 아니면 제한된 로컬 실행이 맡습니다
부채 래칫게이트 끝에서 파일 크기와 중복을 봅니다. 파일은 기록보다 커질 수 없고 새 파일은 800줄 상한입니다. 머지할 때 줄어든 만큼 기록을 낮춥니다
머지 준비[머지]를 누르면 PR 브랜치에서 위키 lint 수리, 문서 인덱스, .omm 구조 문서 갱신을 커밋합니다. 그래서 커밋이 바뀌면 다시 리뷰와 게이트를 거칩니다. 남은 P2 지적은 PR 댓글로 남깁니다

Claude Code Cloud에서 구현한 작업은 이 PC의 .env와 데이터로 검증 영수증을 먼저 받습니다. 저장소가 등록한 사용자 흐름 중 필요한 검사는 Jev가 고르고, 실패하면 로컬 구현으로 넘기지 않고 Cloud로 돌려보냅니다.

대화창 위의 [계획 세우기]는 세 역할로 돕니다. 계획자는 저장소의 계획과 결정을 읽고, 범위를 바꾸는 결정은 선택지로 묻습니다. 그다음 웹을 조사해 출처가 붙은 새 계획 폴더(개요와 단계 문서)를 쓰고 PR을 올립니다. 그 뒤 수정자가 지적을 고치고, 별도의 리뷰어가 계획 기준으로 읽습니다. 시작 전에 시간 · 호출 · 토큰 한도를 정하며, 계획이 승인돼도 구현이나 머지는 저절로 시작하지 않습니다.

리팩터링

빨리 쓴 코드의 빚을, 동작은 그대로 두고 갚는다

에이전트가 빠르게 쓴 코드는 한 번에 리뷰하기 어려울 만큼 커집니다. 이 저장소도 도입 당시 핵심 파일 하나가 3,800줄이었습니다. 리팩터링 포커스는 목적 하나를 골라 저장소를 읽기 전용으로 조사합니다.

조사는 기준 커밋을 따로 꺼낸 작업트리에서 게이트를 기록하고, 파이프라인 지도와 파이프라인별 보고, 실행할 명세 카드를 만듭니다. 카드는 보통 작업처럼 시작하되 테스트 계약이 붙습니다. 기존 테스트 파일은 구문 트리가 같거나 줄만 늘어야 하고, 마지막 검사 결과는 조사 때의 기준선과 비교된 뒤에야 PR이 열립니다.

    python -m pip install -r requirements-hooks.txt
  2. 대상 프로젝트에 .wiki/adapter.toml 만들기

    그 프로젝트의 실제 검사 명령으로 채웁니다. adapters/example.toml은 가짜 예시입니다.

    agents = ["claude", "codex"]

[slots]
review_dir   = "artifacts/review"
gate_cmd     = "python -m pytest"
live_cmd     = "confirm the real events in a new session"
server_stop  = "Ctrl+C in the terminal that started it"
scratch_dirs = "artifacts/"
  3. 위키 버전 고정

    위키 폴더에서 git rev-parse HEAD를 실행하고, 나온 40자를 대상 프로젝트의 .wiki/wiki-revision에 한 줄로 저장합니다(UTF-8, BOM 없음, LF).

  4. Codex를 쓴다면 훅 켜기

    대상 프로젝트의 .codex/config.toml에 추가합니다. 파일이 있으면 덮지 말고 이 항목만 더합니다.

    [features]
hooks = true
  5. 설치하고 확인

    위키 폴더에서 실행합니다. 하나만 쓰면 --agent claude 또는 --agent codex.

    python tool/setup_agents.py --project "../내-프로젝트" --agent both
python tool/setup_agents.py --project "../내-프로젝트" --agent both --check  # 읽기만
  6. 새 세션에서 실제로 확인

    --check 통과는 배선 확인일 뿐입니다. 새 세션을 열어 프로젝트와 훅을 직접 신뢰한 뒤, 세션 시작 정보가 오는지, 규칙을 묻는 말에 그 규칙이 붙는지 봅니다.

프로젝트나 위키를 옮겼다면 같은 명령으로 다시 설치합니다. 위키 버전을 올릴 때는 변경을 검토하고 wiki-revision을 새 값으로 바꾼 뒤 재설치합니다.

C · 휴대폰 연결

밖에서 휴대폰으로 이어 보기

A의 앱 실행휴대폰 브라우저
  1. 외부 연결 켜기

    PC 앱에서 설정 → 휴대폰 → 외부 연결 켜기를 누릅니다. 터널 준비는 앱이 알아서 하고, 준비되면 연결 QR이 나옵니다. VPN이나 포트포워딩은 필요 없습니다.

  2. QR 찍기

    휴대폰 카메라로 QR을 찍어 브라우저로 엽니다. 작업 목록, 대화, 선택한 작업을 보고 지시나 승인을 보낼 수 있습니다. 안드로이드 앱(APK)은 선택입니다.

연결 링크는 한 번만, 5분 안에 쓸 수 있습니다. 그 링크를 연 사람은 이 PC의 작업을 조종할 수 있으니 남에게 보여 주지 마세요. PC와 앱이 켜져 있어야 이어집니다.
