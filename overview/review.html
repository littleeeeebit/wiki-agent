리뷰를 돌려 머지하기

PR이 올라가면 작업한 에이전트와 다른 칸이 코드를 읽기만 하며 리뷰해요. 지적이 나오면 작업 쪽이 고치고, 리뷰가 “머지 허용”을 낼 때까지 라운드를 돌아요. 머지는 허용된 바로 그 커밋으로만 해요.

이걸로 푸는 문제일한 에이전트가 자기 일을 스스로 검사하면 놓친 걸 또 놓쳐요. 그리고 리뷰 루프를 돌리려면 매번 “리뷰 루프 돌려”라고 직접 쳐야 했어요.

실제 기록

다섯 라운드 만에 머지된 PR 하나

이 저장소의 앱 화면과 지도를 만든 PR이 실제로 거친 라운드예요. P1은 머지를 막는 지적, P2는 막지는 않지만 남겨 둘 지적이에요.

라운드마다 지적은 파일과 줄 번호를 달고 와요. 작업 쪽은 그 지적만 고치고, 고친 커밋으로 다음 라운드가 돌아요. 사람은 라운드 결과를 보다가 마지막에 [머지]만 누르면 돼요.

  1. 라운드 1고쳐야 해요P1 둘, P2 하나. 지도에서 문서 목록과 링크 방향이 거꾸로였어요.
  2. 라운드 2고쳐야 해요P1 하나. 설정 창이 서버 값을 받기 전에 열려서, 틀린 값을 보여 주고 덮어쓸 수 있었어요.
  3. 라운드 3고쳐야 해요P1 하나. 프로젝트를 바꾼 뒤에도 이전 저장소에서 고른 PR로 새 저장소의 루프가 시작될 수 있었어요.
  4. 라운드 4고쳐야 해요P1 하나. 화면이 PR 목록을 새로 받지 않고 낡은 목록을 그대로 썼어요.
  5. 라운드 5머지 허용P1 없음. 남은 P2 하나는 PR 댓글로 남기고 머지했어요.

누가

리뷰는 따로 떨어진 칸에서 읽기만 해요

리뷰를 맡는 칸은 작업 칸과 분리돼 있고, 파일을 고칠 수 없어요. 일한 모델과 다른 모델을 고를 수도 있어요. 여러 PR의 루프를 동시에 돌릴 수 있고, 동시에 몇 개까지 돌릴지는 설정에서 정해요.

리뷰 기준도 PR마다 달라요. 계획 문서만 바꾼 PR, 코드를 바꾼 PR, 둘 다 바꾼 PR은 서로 다른 기준으로 읽어요. 리팩터링 PR은 얼려 둔 동작 보존 검사를 라운드마다 다시 돌리고, 그 약속이 바뀌면 이전 승인을 무효로 해요.

막힐 때

같은 지적이 돌아오면 조사부터 해요

고쳤다던 심각한 지적이 다시 나오거나(A → A, A → B → A), 일곱 번째 라운드에서도 거절되면, 다음 수정 전에 웹 조사를 먼저 해요. 같은 문제를 조사하고 고치기를 두 번 했는데도 안 되면 루프를 멈추고 사람에게 넘겨요.

구현을 계속하기 전에 독립된 판단이 필요한 작업은 먼저 읽기 전용 칸의 판정을 받아요. 이 판정은 구현을 계속하게 해 줄 뿐, 마지막 머지 허용을 대신하지는 않아요.

머지

머지는 허용된 그 커밋으로만 해요

  1. 관련 검사만수정 라운드에서는 바뀐 파일에 해당하는 검사만 돌려요
  2. 최종 게이트 한 번리뷰가 허용한 커밋에서 전체 검사를 한 번 돌려요. CI가 있으면 CI가 맡아요
  3. 래칫파일이 기록된 크기보다 커졌거나, 새 파일이 800줄을 넘으면 막아요
  4. [머지]위키 검사 수리, 문서 목록, 구조 문서 갱신을 커밋해요. 커밋이 바뀌었으니 리뷰와 게이트를 다시 거쳐요
  5. 결정 기록명세의 결정과 이유가 저장소에 남고, 다음 세션을 열 때 다시 실려요

머지 직전에 커밋이 하나라도 바뀌면 그 커밋은 리뷰를 받은 적이 없는 거예요. 그래서 머지 준비가 만든 커밋도 다시 리뷰와 게이트를 거쳐요. 번거롭지만, 리뷰가 본 것과 머지되는 것이 같다는 걸 보장하는 방법이에요.

머지된 명세의 결정과 이유는 .wiki/decisions/에 쌓여요. 나중에 누가 그 결정을 뒤집으려 하면, 세션을 열 때 실린 이유를 먼저 읽게 돼요.

Cloud에서 구현한 작업Claude Code Cloud에서 구현한 작업은 이 PC의 .env와 데이터로 실제로 돌려 본 검증 기록을 먼저 받아요. 실패하면 Cloud로 돌려보내요.
